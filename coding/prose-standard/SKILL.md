# 文字与注释写作标准

判断一段文字(注释、文档、错误信息、提示文案)该写什么、怎么写、哪些该删。
核心思想来自 deepseek-harness 的 `dsh-prose-standard` 和 `dsh-doc-standards`,
落地为个人通用版本。

**本规范是判断标准,不是自动缩短工具。** 有些地方需要删,有些地方需要加。
"字更少"不是目标,"信息完整且没有废话"才是。

## 核心原则:保留完整命题

动任何文字之前,先找出这段话包含的每一个事实成分:

- 主体和动作(谁做什么)
- 条件和时序(何时、什么前提下)
- 情态(must / may / never)
- 否定保证和例外(什么情况下**不**成立)
- 所有权、副作用、失败模式、后果

改写时只删修饰语、重复、叙述, **每个事实成分都要存活**。示例:

❌ 过度精简:"协调器串行化持久化。"
✅ 完整保留:"协调器按会话串行化写入,disposal 完成前冲刷缓冲事件,后端失败会回报调用方。"
(按会话、冲刷时序、失败可见性是三个独立事实,删掉任何一个就丢了信息。)

## 一个事实只有一个家

- 完整解释放在**一个**地方(文档、规范、README),其他地方**链接**过去。
- 调用点需要立即能懂的契约(行为、失败、所有权、后果)可以局部写全,
  但架构理由、历史、扩展例子一律链接,不重复。
- 同一段理由出现在多个相似注释里:留一个,其余链接。

## 按位置分类的必需覆盖

### 公共 JSDoc / API 注释
必须覆盖:返回值区分、抛错/拒绝、副作用、所有权、时序、取消、持久性。
不写:函数体流程复述("先取配置再发请求")。

### 内部注释
只写代码表达不了的**非显然契约**:不变量、竞态顺序、所有权、安全边界、
意外的失败行为。删掉控制流叙述和代码复述。

### README
覆盖消费契约:配置、语义、失败、局限、扩展点。不写:生成目录的复述、清单式待办。

### 测试
只解释非显然的测试设计(为什么要这个 fixture、为什么断言外部结果)。
不写:测试步骤讲解("先构造 A,再调用 B,断言 C")。

### 错误信息 / 提示文案
指明:失败的主体或路径、违反的规则、修正方法(不显然时)。
不写:内部执行过程的叙述。

### 提示词(prompt)和可见字符串
措辞就是行为。改了措辞要验证生成输出,不能只改文字。

## 必须删除的内容

- 控制流叙述("首先我们 X,然后我们 Y")
- 代码复述(注释把代码翻译成人话)
- 变更历史("之前是 X,现在改成 Y""v1 这样,v2 那样")
- 测试 walkthrough、评审记录("评审时指出……")
- 防御式自证("这里转换是安全的,因为……")
- 占位式承诺("暂时这样,以后再说")——要么改成 TODO(name) 标记,要么删

判定一句话去留:**"删掉它,读者(一个月后的你/同事/Agent)会不会误解或误改?"**
不会,就删。

## 保留非显然的理由

当"为什么这样写"的缺失可能导致误用或错误简化时,保留理由。
用一两句话 + 链接指回家,而不是长篇论证。

## 工作流程

1. **确认范围**:一次任务只处理明确的范围(某个文件、某个模块、整份文档)。
   范围不明确时先问,不擅自扩大。
2. **先读后改**:判断一段注释前,先读它所属的代码/文档,理解上下文。
3. **逐条分类**:每个候选段落标记为 保留 / 增加 / 精简 / 删除 / 重构 / 暂缓。
4. **应用改动**:任务授权改才改;不给删除任务凑删除量。
5. **改完自检**:重新通读,确认没有误删事实、没有破坏完整性。
6. **报告**:说明审了什么范围、删了什么、刻意保留了什么、哪些拿不准。

## 边界情况处理

- 两版改写都满足"完整命题"但风格取舍不同 → 这是真正的边界,拿出 2-3 个候选,
  说明事实/结构差异,推荐一个。
- 只有一版是正确的 → 直接改,不用问。
- 自动模式下:清晰改动直接执行,拿不准的**记录**为边界情况,不硬改。
