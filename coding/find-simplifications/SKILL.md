# 代码简化审计

把"找简化点"的宽泛请求,变成**有证据支撑的删除/折叠提案**。**本规范是指导,不是清单**:跟着代码走,保持判断力;宁可几个证据扎实的候选,不要一堆猜测。

## 强候选的标准

一个简化是"强候选",当它满足**删除的是真东西 + 有清晰证据证明当前设计成本大于收益**:

- 公共方法、事件、配置项、辅助函数、包、测试产物**没有生产消费者**。
- 只有测试或文档在用,且它们钉住的行为不承重。
- 两个表示镜像同一事实(如持久化事件和瞬态事件重复记录同一状态)。
- 一个 seam/接口有每个实现都必须支持、但无人使用的方法。
- 独立存在的包只是为了测试/演示代码,增加发布和维护开销。
- 投机性产品通用化:多会话、后台任务、实时注册表失效、mid-turn 转向等没有产品主人的设计。
- 只为保护未使用 API 而存在的不变量、回滚路径、特殊用例测试。
- 手写代码重新实现了维护良好的库或语言内置能力,且替换能删除实现 + 其专属测试。
- 简化后行为略有不同,但新行为仍然合理且更容易解释。

## 调查方法

1. **先读仓库规范**(AGENTS.md)和架构文档,理解哪些是故意设计——双后端、双适配器这类"双份"默认是故意的,不要提议"低成本删掉"。
2. **符号级搜索**:用 `rg` 精确符号名(方法名带 `.name(` 和 `name(` 两种写法、事件名、配置键、包名、wire 字符串),然后**读调用点**。`knip` 可辅助,但不能替代对公共接口、动态事件名、加载路径的理解。
3. **从最大的生产代码差异开始**:只找没用符号的审计,可能漏掉重复生命周期/防御性机制最重的地方。
4. 用户要求广度时,可用并行 subagent 分域调查,每个域要求证据,不许猜。

## 消费者分类(写提案前必做)

- **生产语料**:`src/`、运行时脚本、加载/配置路径。
- **非生产语料**:测试、README/docs、快照、注释。
- **模糊地带**:examples、scripts——先读用法再归类。

## 驳回或降级一个候选

- 有生产调用者,且简化是功能决策而非清理。
- 被已记录的决策或防御模式明确辩护,新证据不足以胜过旧理由。
- 删除会迫使无关改动,却不减少公共 API 或必需行为。
- 想法正确但太小:改成内联 `TODO(name):` 标记,不是 skill 级提案。

## 输出:提案 vs 内联标记

- **值得决策的**:写一份简短提案(Problem / Proposal / What we give up / Risks),具体到"删哪个符号、改哪些文件",让后续可以照着执行。避免"简化这个包"这种模糊提案。
- **小清理**:内联 `TODO(name):` + 一句话说明为什么安全、什么动作能简化。
- 一个提案**不重复**已有的决策记录;重叠时合并进现有记录。

## 边界

- 不把代码简化审计自动扩大成整个仓库的决策记录审计。
- 不提议删除被明确记录为故意的设计(双后端、受保护 seam 内的无用方法可删,但塌掉保护设计不行)。
- 简化提案涉及行为变化时,先确认用户接受"行为略有不同但更合理"。
