# 清理思维链残留 (Chain-of-Thought Leakage)

**思维链残留** = 文字的作者视角停留在"写作会话"里,而不是"仓库/代码现状"里:
引用了只有会话内才能看到的东西、叙述"改了什么"而不是"现在是什么"、
或者在对一个已经离开的评审者说话。

判定标准一句话:

> **一个只看当前代码/文档(HEAD)、不接触任何会话记录、PR 评论、未提交草稿的读者,
> 能否理解并验证这句话?**

能 → 不是残留(哪怕听起来像历史)。不能 → 是残留,处理。

## 8 类残留分类

| # | 类型 | 例子 | 处理 |
|---|---|---|---|
| 1 | **死设计会议引用** | `(decision 7)`、`(audit C2)`、`设计稿 §4.7`、`plan §1.4`、阶段标签 `T4`/`W3` | 有正式落地处就指名道姓引用它;否则删掉引用,把事实改写为独立成立 |
| 2 | **PR/栈视角** | "这个 PR 添加了""后面的 PR 会处理""上个 commit 里" | 改写为描述现在的机制或扩展点;推迟的工作改 `TODO(name):` 或 issue 引用 |
| 3 | **变更叙述与版本戳** | "之前是""后来改成""旧的 X 没了""v1 如此、v2 不同""这一版""现在(与过去对比)" | 写现在的行为。修过的 bug 写成现在时反事实:"没有 X 就会 Y" |
| 4 | **评审编排** | "评审时被否了:""reviewer 确认过""本 note 第 5 版" | 保留结论和理由本身,删除"谁在什么时候说过" |
| 5 | **对评审者的自证** | "这个转换是安全的,它只是……""这样做是对的,因为……" | 写使代码安全的不变量;代码本身已体现就删掉 |
| 6 | **复述与推导** | "首先我们 X,然后 Y""测试先构造 A 再断言 B""对显而易见的路径的证明" | 删。只留非显然的契约或不变量 |
| 7 | **占位与计划残留** | "暂时这样应该够""先凑合""以后再说" | 升级为 `TODO(name):`/`FIXME` 或写清实际边界;否则删除 |
| 8 | **写作语言残留** | 中文正文里混入的 `---- 私有 ----`、未翻译的工作语言碎片;或英文正文里混入中文工作碎片 | 翻译或删除 |

## 什么"看起来像残留"但必须保留

清理时不要删错,以下都是**正当内容**:

- **Issue 引用**:`#1470`、`TODO(name):`、`issue #X 负责跟进` —— 在 HEAD 处可解析,保留
- **实测边界**:`(实测:512 层嵌套 ≈ 0.15s)` —— "实测"这个词本身是证据
- **抑制理由**:`oxlint-disable … -- 原因`、空 catch 的解释 —— 有理由要留,理由错了修理由,不删
- **反事实回归钉**:`没有 X 就会发生 Y`、`朴素的 X 实现会……`
- **运行时新旧状态**:`旧连接排空后新连接才接管` —— 这是运行时生命周期,不是变更历史
- **外部标准引用**:RFC 9110 §10.1.5、Figma 页面名 —— 仓库外可解析,合理
- **项目口吻**:"我们"作为项目语气、笔记里"备选方案"章节

## 处理流程

1. **先审计,后修改**:通读范围内最密集的文字(模块 JSDoc、README、笔记),
   标记每个可疑段落。先用分类表判断,不急着删。
2. **逐段枚举事实**:动手删之前,列出这段话的全部事实成分(见 prose-standard
   的完整命题原则)。
3. **先修源,后修衍生品**:生成的内容(目录、快照、双语文档配对)先改源头,
   再重新生成。**双向语言的配对**,两边都要同步改。
4. **警惕过度删除**四种错误:把义务改成建议(把 must 删成 may)、把假设说成
   已上线功能、删掉真实事实、删掉证据来源。
5. **验证**:改完重读,确认每个残留引用都能在 HEAD 处解析、事实完整、
   代码/文档仍正确。

## 配合使用

- 判断"这段该不该留、怎么改"拿不准时,用 `prose-standard`(本 skill 的
  完整命题原则的母规范)。
- 改完文档后运行项目相关的检查(文档、链接、格式),确认没有破坏。
