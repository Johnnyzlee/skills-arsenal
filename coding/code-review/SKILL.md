# 代码评审规范

审查一个 PR 或代码改动时,按本规范执行。**本规范是指导,不是完整清单**——优先正确性、生命周期、安全、破坏性行为,风格问题放最后;一个实质性的阻塞问题比一长串小毛病更有价值。

## 评审前的准备

1. 确认 PR 的实际基线和 head(不信任分支名,用真实 ref)。
2. 用 `git diff <base>...<head>` 或 `gh pr diff` 获取完整改动。
3. 读改动涉及的周边代码,理解设计意图,而不是只看 diff。
4. 有设计文档/决策记录(如我们的 AGENTS.md、skill 来源说明)时对照阅读;与文档有分歧当作设计讨论,不自动否决。

## 阻塞性要求(不满足必须指出)

1. **新文字要语义评审**:所有新增/修改的 Markdown、注释、JSDoc、提示词、错误信息,用 `prose-standard` 评审——覆盖是否完整、准确、该删的废话删了没。自动化检查证明不了这些。
2. **文档与代码同步**:改配置、默认值、错误、接口、行为,必须同步改 README 和 JSDoc;注释描述非显然契约,不写流程复述、测试讲解、变更历史。
3. **必需证据存在**:改动者应该运行了覆盖本次改动的最小相关检查(见 `pre-push-checks`);CI 覆盖完整矩阵;审查自动化检测不到的语义空白。

## 人工检查清单

- **接口契约**:改动接口的两端都看——实现是否匹配声明,包括错误、取消、所有权、释放。新增公共方法只有单一内部调用者是"不必要的 API 扩张",应改为构造时传入私有能力闭包。
- **生命周期与并发**:异步设置、回调、进程、销毁——检查发布前竞态、await 期间取消、独立错误上报、回调隔离、销毁到静止。用简单的语言问:资源会不会泄漏?时序会不会有窗口?
- **范围与必要性**:每个抽象、状态机、选项、防御性拷贝都能对应到真实消费者;质疑无关功能、投机性通用("将来可能用到"不是理由)。
- **配置与默认值**:每个默认值、公开操作集、格式都有消费者证据或先例支撑;没有证据的要么明确选择、要么明确推迟。
- **模型视角**:改动涉及的提示词、工具 schema、模型可见输出是否一致;稳定文本要逐字验证,动态行为要靠快照或端到端测试。
- **边界覆盖**:找到完整结果的拥有者(含包装器、元数据),测试小值/精确边界/超大块/多字节文本的字节限制。
- **真实入口路径**:测试要走真实加载路径(bin、worker、MCP bridge、subprocess),手工挂载的插件发现不了导出错误。
- **测试强度**:断言要能验证外部结果、日志、事件、释放,而不是复述实现;覆盖率高不等于场景正确。
- **执行路径**:任何拒绝/禁止逻辑,追到真正执行的那个操作;尝试能绕过 schema、facade、wrapper 的替代调用者。
- **借用与派生状态**:每个保留的值是借用还是拥有;通知、缓存、回放、查询视图都要能追踪到文档化的成功点和权威来源。

## 报告方式

- 陈述:缺陷是什么、在哪、影响、证据。
- 局部缺陷:内联注释放在 diff 最精确的行上;跨切面的架构问题:PR 级评论。
- 阻塞项与建议分开;已被绿色门禁保证的问题不重复提。
- 收到评审时,逐条核实,技术上成立就修、不成立就反驳,不做表演式认同。

## 边界

- 只评审请求的范围;发现范围外问题记下来提醒,不无限扩散。
- 双语改动(如中英文档配对)要两侧语义都看,hash 一致不代表翻译质量好。
